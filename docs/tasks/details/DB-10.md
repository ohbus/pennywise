# DB-10 — Add causal read-after-write propagation

Define and propagate a writer commit watermark through service responses and
BFF REST/GraphQL requests. A replica may serve a follow-up query only after it
has replayed the watermark; otherwise route to the writer until the deadline.

Acceptance covers command response, HTTP propagation, BFF fanout, WebSocket
hint recovery, lagging readers, timeout, and no-watermark behavior without
using wall-clock time as the causal mechanism.

## Concrete code targets

- Add watermark/value types and propagation support in `libs/db`.
- Add response/request metadata handling in Accounts, Expense Core, Notifications REST clients, and BFF gateway clients.
- Update BFF GraphQL query/mutation resolvers and REST gateway adapters; do not add database access to `app/bff`.
- Extend Expense Core sync revision handling (`JpaSynchronizationStore.kt`, `SyncController.kt`) only where the existing revision is semantically suitable; do not equate every domain revision with PostgreSQL replay LSN without documentation.
- Add integration tests for command response followed by query, BFF fanout, stale reader, and writer fallback under `app/bff/src/test`, service tests, and `tests/acceptance/`.

## Current increment

`libs/db` now models a causal position as a PostgreSQL LSN rather than a wall
clock value. Reader health stores the latest replayed watermark, and a query
with a required watermark cannot use a reader until that position is observed;
eventual/bounded queries use the explicit bounded writer fallback while other
queries remain writer-routed. HTTP/service propagation and command response
headers remain open.
