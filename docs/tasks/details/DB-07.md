# DB-07 — Expense Core read-model and performance pilot

Convert one approved historical/search capability to an explicit read DTO and
query policy. Add stable keyset pagination where appropriate, required indexes,
bounded projections, and baseline/after PostgreSQL plans without changing
financial semantics.

Acceptance includes authorization tests, route tests, stale-read documentation,
`EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)` evidence, representative load
results, and rollback to the writer.

## Concrete code targets

- Start with `app/expense-core/.../search/JpaSearchStore.kt`, `SearchStore.kt`, `SearchController.kt`, and `ExpenseSearch.kt`.
- Replace entity/materialized aggregate reads with a dedicated immutable search projection/DTO and an explicit `ReadPolicy` operation name.
- Review `ExpenseRepository.kt` and `BalancePostingRepository.kt` for list/detail queries; do not move balance or authorization reads to readers in this task.
- Add only required indexes through a new Expense Core Flyway migration under `src/main/resources/db/migration/` after capturing the current plan.
- Extend `JpaSearchStoreTest` and add a PostgreSQL plan/route integration test under `app/expense-core/src/test`.

## Current implementation increment

`SearchController` now performs writer-based membership authorization first,
then scopes only `expense.search` and `expense.search.export` as eventual,
reader-eligible operations. The optional replica Compose override enables the
Expense Core routed datasource with the writer at `postgres-db` and the search
reader at `postgres-replica-db`. The repository now applies description,
currency, category, and UUID keyset cursor filtering in SQL, returns a scalar
projection, and fetches one extra row for bounded `hasMore` detection. The
existing response/domain layer still owns totals and CSV formatting.
